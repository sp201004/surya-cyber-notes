## Objective

In cybersecurity, **logs are the digital footprints left behind by activities performed on a system**. Whenever something happens on a computer, server, application, or network — a login, a network connection, a process execution, a file access — information about that activity can be recorded in a log. Because attackers, even when they try to hide, leave traces across multiple systems, logs become the single most valuable source of evidence during **security monitoring** and **incident investigation**. This room builds the foundation: what logs are and why they matter, the different **log types** and **sources**, how logs are structured, where they live on **Windows** and **Linux**, and how to analyse them manually with **Event Viewer** and the core Linux commands `cat`, `grep`, and `less`.

By the end of this room you will be able to:

- Explain what **logs** are and why they are critical evidence in cybersecurity
- Describe the major **use cases** of logs — security monitoring, incident investigation, forensics, troubleshooting, performance monitoring, and auditing/compliance
- Identify the six main **log types**: System, Security, Application, Audit, Network, and Access logs
- Investigate **Windows Event Logs** with **Event Viewer**, reading the Description, Log Name, Logged, and Event ID fields
- Recognise important **Windows Event IDs** (`4624`, `4625`, `4634`, `4720`, `4722`, `4724`, `4725`, `4726`)
- Read the structure of an **Apache access log** and locate it at `/var/log/apache2/access.log`
- Break an access-log entry into its fields — IP, timestamp, HTTP method, URL, status code, User-Agent
- Analyse logs on Linux with `cat`, `grep`, and `less`, and combine filters with the pipe (`|`) operator
- Build a **timeline** and **correlate** multiple log sources to reconstruct an incident

> **Core idea:** *Logs are the digital footprints of a system.* If something happened, there is a good chance evidence of it exists in a log somewhere.

## Task 1 — Introduction to Logs

A **log** is a record of an activity or event generated by a system, application, network device, or other component. Logs record both **normal** activities and **suspicious or malicious** ones, which is why they are indispensable during security monitoring and incident investigation.

Think of a physical crime scene — a broken door, footprints, CCTV footage all become evidence that leads to identifying a criminal. The digital world works the same way: a login event, network connection, process execution, or file access all flow into logs, and those logs drive the investigation that identifies an attacker.

During an incident, logs help the security team answer the key investigative questions:

`WHO? → WHAT? → WHEN? → WHERE? → HOW?`

For example, a single authentication record can tell an analyst a great deal, which they then correlate with other logs to understand the full picture:

```text
Time        : 10:42 PM
Source IP   : 192.168.1.50
User        : administrator
Activity    : Successful login
System      : File Server
```

### Major Use Cases of Logs

Logs serve several purposes across cybersecurity and IT operations:

> **1. Security Events Monitoring**
> Logs help security teams detect anomalous or suspicious behaviour during real-time monitoring. A user who normally logs in from India at 09:00 AM on a company laptop, then suddenly appears at 03:00 AM from an unknown IP in a different location, is an anomaly surfaced through logs. Flow: `Logs → Monitoring → Detect Anomaly → Generate Alert → Investigate`.

> **2. Incident Investigation & Forensics**
> Logs contain traces of the activities that occurred during an incident, letting teams reconstruct what happened. By correlating events such as `10:01 Failed login → 10:03 Successful login → 10:05 New account created → 10:08 Suspicious process → 10:12 File server accessed → 10:15 Sensitive file downloaded`, analysts build an **incident timeline** and perform root-cause analysis.

> **3. Troubleshooting**
> Logs are also extremely useful for troubleshooting operating systems and applications: `Application crashes → Check application logs → Find error → Identify cause → Fix problem`. They commonly contain errors, warnings, service failures, configuration problems, and compatibility issues.

> **4. Performance Monitoring**
> Logs provide information about the performance of applications and systems. A response time that climbs `100 ms → 150 ms → 400 ms → 900 ms → 2000 ms` may indicate a performance problem.

> **5. Auditing & Compliance**
> Organizations may need to keep records of activities performed on their systems. Logs provide an **audit trail** — who accessed a system, when, what resource, what changes were made, and which account performed the action.

### What Is Log Analysis?

> **Log Analysis** is the process of examining logs to extract valuable information and identify abnormal or suspicious activities.

The basic workflow reduces a large volume of raw data into a conclusion:

`Logs → Collect Information → Filter Events → Search for Patterns → Identify Anomalies → Correlate Data → Investigate → Determine Root Cause`

Depending on the log type, an analyst may find fields such as Timestamp, IP Address, Username, Hostname, Process, File, URL, HTTP Method, Status Code, User-Agent, Event ID, Authentication Result, Network Connection, and Error Message — combining them to understand an incident.

### Log Correlation

One log alone rarely tells the complete story. Multiple logs are correlated to reconstruct an incident:

`Security Log (successful login) + Network Log (connection from suspicious IP) + Application Log (sensitive file accessed) + Firewall Log (large outbound connection) → Possible Data Exfiltration`

This concept is central to **SOC / SIEM / Incident Response**. A simplified SOC flow: `Systems → Logs → Log Collection → SIEM/Platform → Correlation → Alert → SOC Analyst → Investigation → Benign (Close) or Malicious (Incident Response)`.

## Task 2 — Types of Logs

A single huge log file mixing logins, startups, network connections, application errors, file access, and password changes would be very difficult to search. To make investigation easier, logs are separated into categories according to the type of information they provide, so analysts can focus on the log type relevant to their investigation. The room introduces six important categories:

> **1. System Logs**
> Record information related to the operating system and its activities — system startup and shutdown events, driver loading, system errors, and hardware events. Main purpose: **troubleshooting** OS-related problems.

> **2. Security Logs**
> Contain information about security-related activities: authentication events, authorization events, security policy changes, user account changes, and abnormal activity. Extremely important during cybersecurity investigations (who logged in, when, from where, and whether the login was legitimate).

> **3. Application Logs**
> Contain events related specifically to applications running on a system — user interaction events, application changes, update events, and error events. Help developers and analysts understand what happened inside an application.

> **4. Audit Logs**
> Provide detailed information about system changes and user activities — data access events, system change events, user activity events, and policy enforcement events. Especially useful for compliance, security monitoring, investigations, and tracking changes.

> **5. Network Logs**
> Contain information about incoming and outgoing network traffic — network connections and firewall events. Useful for network troubleshooting, incident investigation, detecting suspicious connections, and understanding network activity.

> **6. Access Logs**
> Provide information about access to resources such as websites, databases, applications, and APIs. Examples include Webserver, Database, Application, and API access logs — especially important for web-server investigations.

### Authentication vs Authorization

These terms are important when working with security logs:

- **Authentication = "Who are you?"** — `Username + Password → Authentication → Identity verified`.
- **Authorization = "What are you allowed to do?"** — an authenticated user like Alice can access public files and company documents, but not administrator settings.

### Security Logs vs Audit Logs

These two can look similar. The distinction:

- **Security logs** ask: *"Is something security-related happening?"* (authentication, authorization, account changes, abnormal activity).
- **Audit logs** ask: *"Who did what, and when?"* (a detailed activity trail of user actions, system changes, data access, policy enforcement).

### Web Server Access Logs (preview)

A web server receives many requests (`GET /`, `GET /login`, `POST /login`, `POST /upload`, `GET /admin`). A typical access log records the Source IP, Timestamp, HTTP Method, URL, Status Code, and User-Agent — for example `192.168.1.10`, `06/Jun/2024:13:55:44`, `POST`, `/login`, `200`, `Mozilla/5.0`. These are analysed in detail in Task 4.

## Task 3 — Windows Event Logs Analysis

Just like other operating systems, **Windows records many activities** and stores them in separate log files based on category. The three important Windows logs are:

> **1. Application**
> Contains information related to applications running on Windows — application errors, warnings, compatibility issues, and application events. When an application crashes, Windows records the event here for an analyst to investigate.

> **2. System**
> Records activities related to the Windows operating system itself — driver issues, hardware issues, system startup and shutdown, service information, and system errors. If a driver fails to load: `Driver Failure → System Event → System Log → Troubleshooting`.

> **3. Security**
> One of the most important logs from a cybersecurity perspective. Records security-related activities such as user authentication, account changes, security policy changes, and logon/logoff events: `User Login → Authentication Event → Security Log → SOC Investigation`.

### Windows Event Viewer

Windows provides a graphical utility called **Event Viewer** that lets analysts view, search, filter, and investigate events. Open it from the Start menu (`Start → Search → Event Viewer → Open`). Its structure looks like this:

```text
Event Viewer
│
├── Custom Views
│
├── Windows Logs
│   ├── Application
│   ├── Security
│   ├── Setup
│   ├── System
│   └── Forwarded Events
│
├── Applications and Services Logs
│
├── Saved Logs
│
└── Subscriptions
```

For cybersecurity investigations, the **Security** log under **Windows Logs** is particularly important. To investigate: `Event Viewer → Windows Logs → Security → View Events`. The Security log can contain a very large number of events (Audit Success / Audit Failure), and each can be double-clicked to view its details.

### Important Event Fields

When you open an event, pay attention to four key fields:

> **1. Description**
> Provides detailed information about the activity — e.g. *"An account was successfully logged on."* Tells the investigator what happened.

> **2. Log Name**
> Tells us which log file contains the event — e.g. `Log Name: Security` means the event belongs to the Windows Security log.

> **3. Logged**
> Tells us when the activity occurred — e.g. `6/24/2024 3:36:31 AM`. Timestamps are essential for building an incident timeline.

> **4. Event ID**
> A unique identifier for a specific type of activity — e.g. `Event ID: 4624` represents a user account that successfully logged in.

### Important Windows Event IDs

Windows generates many events, so analysts search for a specific **Event ID** rather than reading everything. The room introduces these:

| Event ID | Meaning |
|---:|---|
| **4624** | A user account successfully logged in |
| **4625** | A user account failed to log in |
| **4634** | A user account successfully logged off |
| **4720** | A user account was created |
| **4722** | A user account was enabled |
| **4724** | An attempt was made to reset an account's password |
| **4725** | A user account was disabled |
| **4726** | A user account was deleted |

> **Memory pattern:** `46xx → Login / Session` (4624 success, 4625 failure, 4634 logoff); `47xx → Account Management` (4720 create, 4722 enable, 4724 reset password, 4725 disable, 4726 delete). A failed login (`4625`) is not automatically malicious, but repeated unusual failures are a useful investigation lead.

### Filtering Windows Logs

Large Windows logs can contain 22,000+ events, so manual searching is inefficient. Event Viewer provides **Filter Current Log...** to display only events matching specific criteria:

`Open Event Viewer → Select Security Log → Filter Current Log... → Enter Event ID → OK → Review matching events`

Filtering the Security log for `Event ID 4624`, for example, reduces a mixed stream (`4624, 4672, 4634, 4624, 4625, 4672, 4624, 4634 ...`) down to only the successful logon events. **Filtering reduces the amount of data an analyst needs to examine.**

### Timeline Reconstruction

Timestamps from event logs combine to reconstruct an incident. A sequence such as:

`09:01 4625 Failed login → 09:02 4625 Failed login → 09:03 4624 Successful login → 09:05 4720 New account created → 09:06 4722 Account enabled`

would be interpreted as failed attempts, then access, then account creation and enablement — a sequence warranting further investigation.

### Practical Investigation Scenario

The room provides an investigation scenario:

> An organization was a victim of a cyber attack. Critical data was exfiltrated from a file server. The security team identified the username and IP address of the compromised system that accessed the file server.

The goal is to investigate the attacker's activities **before they accessed the file server** by analysing Windows Event Logs. The investigation logic follows the account lifecycle: `4720 Account Created → Created by Administrator → 4722 Account Enabled → 4724 Password Reset`, and the discovered evidence is:

| Evidence | Value |
|---|---|
| Suspicious Account | `hacked` |
| Account Creator | `Administrator` |
| Creation Event | `4720` |
| Account Enabled Event | `4722` |
| Enabled Date | `6/7/2024` |
| Password Reset Event | `4724` |
| Password Reset | Yes |

> **Avoid jumping to conclusions:** the username `hacked` looks suspicious, but the analyst should not conclude it is the attacker based on the name alone. Correlate username + creator + timestamp + logon activity + resource access + network activity before reaching a conclusion.

## Task 4 — Web Server Access Logs Analysis

A **web server access log** records requests made to a web server. Whenever a client interacts with a website, the server records information about the request: `Client → HTTP Request → Web Server → Access Log`. These logs are useful for troubleshooting, traffic analysis, security monitoring, incident response, and attack investigation.

### Apache Access Logs

The room uses **Apache web server** access logs. On a typical Debian/Ubuntu-based Linux system the Apache log directory is `/var/log/apache2/`, which may contain `access.log` (records requests made to the web server) and `error.log` (records errors and other server messages). The common access-log location is:

```text
/var/log/apache2/access.log
```

To display its contents, use `cat`; for a large file, use `less`:

```bash
$ cat /var/log/apache2/access.log
$ less /var/log/apache2/access.log
```

### Access Log Structure

A typical Apache access-log entry contains several fields — IP, timestamp, request, status code, and User-Agent. A simplified entry looks like:

```text
10.0.0.1 - - [06/Jun/2024:13:55:44 +0000] "GET /contact HTTP/1.1" 200 1234 "Mozilla/5.0"
```

Breaking that entry into its individual fields:

| Field | Value | Question it answers |
|---|---|---|
| IP Address | `10.0.0.1` | Who? |
| Timestamp | `06/Jun/2024:13:55:44` | When? |
| HTTP Method | `GET` | What action? |
| Requested URL | `/contact` | Which resource? |
| Status Code | `200` | What result? |
| User-Agent | `Mozilla/5.0` | Which client? |

Each field carries investigative weight:

> **1. IP Address**
> The source address associated with the request (e.g. `10.0.0.1`). An analyst can use it to identify the source, search other requests from it, and build an activity timeline — correlating multiple requests such as `GET /login → GET /admin → POST /contact` from the same source.

> **2. Timestamp**
> When the request occurred (e.g. `06/Jun/2024:13:55:44`). Critical for building a timeline — e.g. `13:50 GET /login → 13:52 GET /admin → 13:55 POST /contact → 13:57 GET /dashboard`.

> **3. HTTP Method**
> The type of request. The room focuses on **GET** (retrieve a resource — *"Give me something."*) and **POST** (submit data — *"I'm sending something."*). POST requests are especially interesting because they may carry submitted information such as login credentials.

> **4. Requested URL**
> Which resource the client requested (e.g. `/`, `/login`, `/admin`, `/dashboard`). Unusual URLs can be investigation clues — `GET /wp-admin` could indicate automated scanning against a WordPress installation. A suspicious URL is a clue, not proof of an attack.

> **5. HTTP Status Code**
> How the server handled the request. Repeated `404` responses (`GET /admin 404 → GET /backup 404 → GET /config 404 → GET /secret 404`) may indicate directory enumeration, scanning, or automated reconnaissance.

> **6. User-Agent**
> Identifies the client (e.g. `Mozilla/5.0`, `curl/8.x`, `python-requests/2.x`). Can hint whether a request came from a browser, script, tool, or automated scanner — but a suspicious User-Agent alone does not prove malicious activity, and it can be spoofed.

### HTTP Status Codes

| Category | Meaning | Important Codes |
|---|---|---|
| **1xx** | Informational | — |
| **2xx** | Success | `200` OK |
| **3xx** | Redirection | `301` Moved Permanently, `302` Found / Redirect |
| **4xx** | Client Error | `400` Bad Request, `401` Unauthorized, `403` Forbidden, `404` Not Found |
| **5xx** | Server Error | `500` Internal Server Error, `502` Bad Gateway, `503` Service Unavailable |

### Investigating with grep

Rather than reading the entire log, search for the field of interest. To find every request from a suspicious IP:

```bash
$ grep "10.0.0.1" access.log
```

To search by HTTP method or URL:

```bash
$ grep "GET" access.log
$ grep "POST" access.log
$ grep "/contact" access.log
```

Combine conditions with the pipe (`|`) operator — for example, POST requests from a specific IP, or GET requests to `/contact`:

```bash
$ grep "POST" access.log | grep "172.16.0.1"
$ grep "GET" access.log | grep "/contact"
```

### Viewing Large Logs with less

`cat access.log` on a 500,000-line file may flood the terminal, so use a pager. `less access.log` lets you view and search large files interactively:

```bash
$ less access.log
```

Useful keys inside `less`:

```text
/keyword → Search
n        → Next match
N        → Previous match
Space    → Forward
b        → Back
q        → Quit
```

### Log Rotation

Web servers rotate logs so no single file grows indefinitely: `access.log` (current), `access.log.1`, `access.log.2`, `access.log.3` (older). If an attack happened yesterday, the relevant evidence may live in `access.log.1`, so **do not investigate only the current log when historical activity matters**. To analyse multiple logs together, combine them:

```bash
$ cat access.log access.log.1 access.log.2 > combined.log
```

### Practical Investigation

The room asks precise questions answered by reading the right field. Search, review all matches, and compare timestamps to find the *last* matching entry (latest timestamp):

```bash
$ grep "GET" access.log | grep "/contact"
$ grep "172.16.0.1" access.log | grep "POST"
```

## Task 5 — Log Analysis with Linux Commands

Log analysis is fundamentally a **filtering problem**: you start with a huge amount of raw data and progressively reduce it — `Raw Logs → Known IOC → Specific IP/User → Specific Time → Specific Method/Event → Specific URL/Resource → Relevant Events → Timeline → Correlation → Investigation`. A SOC analyst rarely reads every entry manually; instead they use command-line tools to view, search, filter, and correlate. The core tools from this room are `cat`, `grep`, `less`, and the pipe operator `|`.

### cat — Display Log Files

`cat` displays the contents of a file (`cat filename`). It is useful for small files, quick inspection, combining files, or piping output to another command:

```bash
$ cat access.log
```

On a large file (e.g. 500,000 lines) `cat` may flood the terminal and you lose the beginning of the output — for those, use `less`.

### less — Read Large Logs

`less` provides interactive viewing without dumping the whole file at once:

```bash
$ less access.log
```

Inside `less`, press `/` and type a keyword to search, `n`/`N` to move between matches, `Space`/`b` to page forward/back, and `q` to quit.

### grep — Search Log Files

`grep` searches text for a specified pattern (`grep "pattern" file`). It is the workhorse of manual log analysis:

```bash
$ grep "ERROR" application.log
$ grep "172.16.0.1" access.log
```

### Combining Conditions with the Pipe

The pipe operator `|` passes the output of one command as input to the next — *"take the result and pass it forward."* Chaining `grep` filters narrows results step by step, from all logs down to exactly the entry you need:

```bash
$ grep "172.16.0.1" access.log | grep "POST"
$ grep "172.16.0.1" access.log | grep "POST" | grep "/contact"
```

Conceptually: `ALL LOGS → Specific IP → POST → /contact → Exact investigation data`.

### First vs Last, and Field-Oriented Searching

Read the question carefully — **FIRST** means the earliest timestamp, **LAST** means the latest. When multiple entries match, review all matches and compare timestamps rather than selecting the first line. Also understand *where* a value appears: `grep "404" access.log` can match any occurrence of the string `404`, not only the HTTP status field. For a lab this is usually sufficient, but production analysis should parse the specific field.

### Searching Rotated Logs

Historical evidence may live in rotated logs. You can search several files at once, or combine them first and search the result:

```bash
$ grep "172.16.0.1" access.log access.log.1 access.log.2
$ cat access.log access.log.1 access.log.2 > combined.log
```

### Correlation and Manual vs SIEM

Manual commands teach the concepts used by larger platforms. In an enterprise, logs from servers, endpoints, firewalls, applications, and the cloud flow into a **SIEM** (Security Information and Event Management) for centralized search, correlation, detection, and alerting: `Log Sources → Log Collection → SIEM → Correlation / Detection → Alert → SOC Analyst`.

| Manual Analysis | SIEM Analysis |
|---|---|
| Good for small datasets | Good for large environments |
| CLI tools (`grep`, `less`, `cat`) | Centralized platform |
| Analyst-driven | Automated correlation |
| Simple investigations | Enterprise investigations |

> **Golden rule of investigation:** Never stop after finding one suspicious line. Ask *what happened before, what happened after, who performed it, which host, which IP, what else did the same source do, and is the activity present elsewhere?* One event may be meaningless; multiple related events reveal the story.

### Linux Log Analysis Cheat Sheet

```bash
# Display file
cat access.log

# Interactive viewing
less access.log

# Search text
grep "pattern" access.log

# Search IP
grep "172.16.0.1" access.log

# Search GET
grep "GET" access.log

# Search POST
grep "POST" access.log

# Search URL
grep "/contact" access.log

# IP + POST
grep "172.16.0.1" access.log | grep "POST"

# GET + URL
grep "GET" access.log | grep "/contact"

# IP + POST + URL
grep "172.16.0.1" access.log | grep "POST" | grep "/contact"

# Search multiple logs
grep "172.16.0.1" access.log access.log.1 access.log.2

# Combine logs
cat access.log access.log.1 access.log.2 > combined.log
```

## Final Takeaway

**Logs** are the **digital footprints** of a system — records of events that become **evidence** during **security monitoring** and **incident investigation**. This room grounds that idea end to end: logs are separated into six **log types** (**System**, **Security**, **Application**, **Audit**, **Network**, **Access**) so analysts can focus on the right source, and **log analysis** turns raw data into understanding through the flow `Collect → Filter → Search → Correlate → Investigate`. On **Windows**, the **Event Viewer** surfaces the **Security** log, where key **Event IDs** — `4624` logon, `4625` failed logon, `4720` account created, `4722` enabled, `4724` password reset — drive account and authentication investigations (the lab traces the account **`hacked`**, created by **`Administrator`**, enabled **`6/7/2024`**, password reset **`Yes`**). On the web, an **Apache access log** at **`/var/log/apache2/access.log`** breaks each request into **IP**, **timestamp**, **HTTP method**, **URL**, **status code**, and **User-Agent** — the *who, when, what, which resource, what result, which client* of every request. On **Linux**, the manual toolkit is **`cat`**, **`less`**, and **`grep`**, chained with the **pipe** (`|`) to filter huge files down to a single relevant entry, always mindful of **log rotation** and rotated files. The recurring lesson is that **suspicious ≠ malicious**: an indicator is only an investigation lead, and the real work is building a **timeline**, **correlating** multiple sources, determining **scope**, and then responding — because one event may be meaningless, but multiple related events reveal the story.
